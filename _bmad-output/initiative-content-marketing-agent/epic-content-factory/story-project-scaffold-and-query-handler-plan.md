## Intent

**Problem:** The repo has no code (the first build was removed in 5c88824), so there is no project, graph, or entry point for any content agent to plug into.

**Approach:** Stand up the uv/LangGraph project and a one-node graph: the Query Handler classifies a request as research, blog, linkedin, or image with a topic and ends with a message naming both. This tracer bullet proves uv, LangGraph state, an LLM call, the LLM error convention, and `langgraph dev` end to end; later entries replace the ending per format.

## Boundaries & Constraints

**Always:**
- Model comes from `OPENAI_MODEL`, default `gpt-4o-mini`, via one `get_llm()` that builds the client lazily so imports and tests never need a key.
- LLM error convention (every later node follows it): OpenAI failures and unparseable structured output are caught in the node and turned into a readable message in `final_output` plus an entry in the per-run `errors` list. `errors` has no reducer; every Query Handler run writes it (empty on success) so a `langgraph dev` thread never carries stale errors.
- Every run overwrites `intent`, `topic`, `final_output`, and `errors`, so a reused thread shows only this run's result.
- An empty or whitespace-only request gets a prompt for a topic without any LLM call.
- LangSmith tracing is optional: `.env.example` lists `LANGSMITH_API_KEY`, `LANGSMITH_TRACING`, `LANGSMITH_PROJECT`; runs work with them unset.
- Tests are offline: fake LLM, no network.

**Never:**
- No research, SerpAPI, writers, image generation, or post-research routing (entries 2–6).
- No README or Cloud packaging work beyond a working `langgraph.json` (entry 7).
- No `operator.add` (or any accumulating) reducer on `errors`.
- Never put the API key or raw request headers in an error message.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Research | "Give me an overview of AI in B2B marketing" | `intent=research`, topic set, `final_output` names intent and topic, `errors=[]` | No error expected |
| Blog | "Write a blog post about remote work tools" | `intent=blog`, topic without format words | No error expected |
| LinkedIn | "LinkedIn post on our product launch" | `intent=linkedin` | No error expected |
| Image | "Make an image of a sunrise over a city" | `intent=image` | No error expected |
| Empty | `""` or `"   "` | `intent=empty`, `topic=""`, `final_output` asks for a topic, `errors=[]`, LLM never called | No error expected |
| LLM fails | OpenAI raises (no key, auth, rate limit, API error) or structured output cannot be parsed | no crash; `final_output` is a readable message; `errors` has one entry naming the node and the failure kind; `intent=error` | caught in node |
| Thread reuse | second run on a thread whose previous run failed | `errors` reflects only the second run | — |

## Implementation Notes

- `build_graph(checkpointer=None)` takes an optional checkpointer so the thread-reuse test can use `InMemorySaver`; the exported `graph` has none (`langgraph dev` supplies its own).
- `llm_error()` uses only the exception class name, never its text, so keys or request details echoed by OpenAI never reach `final_output` or `errors`. `errors` entries are `"query_handler: <ExceptionClass>"`.
- A non-`RouteDecision` structured result is treated as `OutputParserException`.

## Design Notes

`intent` gains two non-classification values: `empty` and `error`. Later routers branch on them to end early, so keep them as plain strings next to the four classified intents rather than adding them to `RouteDecision`'s `Literal` (the LLM must never choose them).
